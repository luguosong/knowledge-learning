# 2026-10-27 · GitHub PR 的完整执行过程

- **问**：GitHub PR（Pull Request）从建分支到合并后的完整执行过程是什么？
- **答**：PR 是 GitHub 的合并提案机制：在 head 分支（源）上提交并推送后，向 base 分支（目标）开启 PR；GitHub 创建只读引用并触发 CI Checks；评审与必需门禁（必需检查、必需批准、无冲突）通过后，以 merge commit、squash 或 rebase 三种方式之一合并；随后删除 head 分支，PR 与提交历史保留，关联 issue 自动关闭。PR 是平台功能，不是 Git 命令。
- **信源**：[一手] [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)；[一手] [About pull requests](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests)；[一手] [About pull request merges](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges)；[一手] [About pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)
- **核实**：2026-10-27；核实了流程步骤、draft PR、PR 只读引用、三种合并方式、评审三种结论与分支保护门禁（GitHub Docs 当前版，适用 Free/Pro/Team 计划）；fork 场景的深层权限差异未展开。

## 各阶段要点

1. **建分支**：从 base 分支（通常为 main）切出 head 分支，命名短且描述性；改动隔离在 head，base 只保留完成并通过审查的工作。
2. **提交并推送**：每个提交保持孤立、完整，便于回滚；推送即远程备份，协作者可见。
3. **开启 PR**：选 head → base，写标题与摘要（改了什么、为什么、如何验证）；描述中用 `Closes #编号` 等关键词关联 issue，合并后自动关闭；自动按 CODEOWNERS 请求评审。GitHub 服务端创建只读引用 `refs/pull/N/head` 与 `refs/pull/N/merge`（模拟合并结果，仅在无冲突时存在），并触发 CI（如 GitHub Actions），结果显示在 Checks 标签页。
4. **草稿 PR（Draft PR）**：不能被合并，不自动请求代码所有者；标记 "Ready for review" 后转为正式 PR 并请求评审。
5. **评审**：有读权限者即可评审，结论三种——Comment（仅评论）、Approve（批准）、Request changes（要求修改）；行内评论可附建议改动。作者向 head 分支继续提交推送，PR 与 Checks 自动更新。
6. **门禁**：合并前必须无合并冲突；仓库的分支保护规则可要求指定数量的批准、必需检查通过或特定团队批准，未满足时合并按钮停用并在合并状态框列明。
7. **合并三方式**：merge commit（保留全部提交并追加合并提交，对应 `--no-ff`）；squash and merge（压成单个提交，快进合入，历史简洁；长生命周期分支不建议，否则后续 PR 会反复冲突）；rebase and merge（逐个提交变基到 base，线性历史，无合并提交；提交 SHA 与提交者信息被改写）。三种均需在仓库设置中开启，合并者需写权限；无写权限者（fork 贡献）由有权限者执行合并。间接合并：head 提交经其他途径已可达 base 时，PR 自动标记为已合并（squash/rebase 除外）。
8. **合并后**：提示删除 head 分支；PR 记录与提交历史保留，分支可恢复，可用"还原（revert）"撤销整个 PR；关联 issue 在此刻自动关闭。
